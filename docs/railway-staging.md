## Конфигурации в репозитории

В deploy/railway подготовлены отдельные JSON и Dockerfile для web, migrator,
Ollama и настоящего ClamAV. Указать каждому сервису свой config file path;
корневой railway.json не добавлен, чтобы случайно не изменить production.
Railway не запускает Docker Compose как оркестратор.

| Сервис | Том | Стартовые лимиты | Доступ |
|---|---|---|---|
| tk-staging-web | /app/storage, 5 GB | RAM 1 GB, CPU 1 | один HTTPS staging-домен |
| tk-staging-postgres | корректный PGDATA, 5 GB | RAM 1 GB, CPU 1 | только private DNS |
| ollama | /models, 15 GB | RAM 16 GB, CPU 4 | только private DNS:11434 |
| clamav | /var/lib/clamav, 5 GB | RAM 4 GB, CPU 1 | только private DNS:3310 |
| tk-staging-migrate | без тома | RAM 2 GB, CPU 1, one-shot | без публичной сети |

Один replica у каждого. Лимиты ресурсов задаются отдельно через Railway settings,
они не являются резервированием памяти. PostgreSQL18 PGDATA сверить по выбранному
официальному шаблону до создания тома; production path не менять.
Ollama private hostname должен быть ровно ollama.railway.internal.
Private network Railway шифрует трафик WireGuard и изолирована по environment.
Не создавать публичные домены/TCP proxy для DB, Ollama или ClamAV.

Модели устанавливаются явной командой администратора в уже запущенном
Ollama service, после подключения постоянного /models. Основная qwen3:8b,
облегчённая qwen3:4b выбирается вручную. Pull не находится в startup,
healthcheck, Docker build или миграциях. Повторный deployment сохраняет том.
Health /api/tags подтверждает сервер; выбранную модель и реальную генерацию
подтверждает дополнительная проверка из web service.

ClamAV требует обновляемых баз FreshClam, постоянного тома, мониторинга
актуальности сигнатур и достаточной памяти. Официальная документация рекомендует
4 GB RAM для контейнера. В runtime-загрузках обязателен CLEAN, обхода нет.
До фактического container/staging прогона эти конфигурации считаются подготовленными.

## Ресурсы и стоимость

Цены контейнеров по [Railway Plans](https://docs.railway.com/pricing/plans):
RAM $10/GB-месяц, CPU $20/vCPU-месяц, volume $0.15/GB-месяц,
egress $0.05/GB; оплачивается измеренное потребление. Подписка/включённый
usage зависят от аккаунта, баланс и bill не доступны проверенными вызовами.

Оценка, не счёт и не обещание производительности:

| Вариант | Допущения steady state | Порядок затрат |
|---|---|---|
| 8B | Ollama 10 GB/1 средний vCPU, ClamAV 4 GB, web 1 GB, DB 0.5 GB, 30 GB volumes | около $180/месяц плюс прочий CPU/egress |
| 8B на лимитах | Ollama 16 GB/4 CPU, ClamAV 4 GB/1 CPU, web и DB по 1 GB/1 CPU | до порядка $365/месяц при постоянной полной нагрузке |
| 4B | Ollama около 6 GB/1 средний CPU, прочие сервисы те же | около $140/месяц плюс прочий CPU/egress |

Формула: average RAM × 10 + average CPU × 20 + volumes GB × 0.15 + egress GB × 0.05.
Для 8B краткая проверка до 4 часов при этих caps — ориентир до $3
вычислений, плюс хранилище/сеть; предложенный предел согласования $5.
Остановка compute не удаляет данные и не отменяет плату за тома.
Постоянную эксплуатацию согласовать отдельно, установить бюджетные уведомления
и доступные Railway spending controls до запуска.

На этой машине обе модели ранее уже установлены. В текущем прогоне 8B прошла
полный HTTP сценарий на публичном PDF примерно за 1.6 минуты. Это время всего
теста на локальном GPU-хосте, не оценка CPU-only Railway. Из прежних измерений
CPU allocation модели 8B около 6.28 GiB, 4B около 3.70 GiB; это не peak RSS.
16 GB RAM для отдельного 8B сервиса — стартовое допущение с резервом,
проверить на целевом CPU, контексте и документе. При нехватке памяти/скорости —
явно 4B или отдельный AI-хост в подходящем регионе, без paid fallback.

## Порядок запуска после согласования

1. Создать **пустой** environment staging-integration в том же проекте.
   Не клонировать production-БД, secrets или documents в тестовую среду.
2. Создать отдельные staging DB/volumes/services согласно таблице, выставить caps.
   Проверить отсутствие подключения к production DATABASE_URL/volume.
3. Задать новые staging secrets в Variables и APP_URL. Resend выключен:
   EMAIL_DOMAIN_VERIFIED=false, ключ/отправитель пустые до действия владельца.
   Тестовый email sink не публиковать; автоматические email-тесты остаются локально/CI.
4. One-shot migrator применяет 12 миграций на пустую staging-БД. Создать
   ограниченную роль scripts/db-roles.sql; только web получает её DATABASE_URL.
   Migrator имеет DDL-доступ, после успешного завершения остановлен.
5. Подключить volumes до старта, установить модель один раз, запустить
   настоящий ClamAV и проверить CLEAN PDF / EICAR.
6. Развернуть integration SHA, /api/health, login/registration/MFA,
   manual RADAR import, saved searches, GUARD revisions и финансовый отчёт.
   Только синтетические аккаунты и публичные/обезличенные документы.
7. Проверить реальную Qwen3 на PDF, память/CPU/latency, отсутствие облачного
   fallback и утечки между компаниями, сохранность моделей после redeploy.
8. Проверить trusted client IP и маскирование reset query в ingress logs/APM.
   [Railway документирует X-Real-IP](https://docs.railway.com/networking/public-networking/specs-and-limits);
   приложение выбирает его в Railway и игнорирует X-Forwarded-For.
   Без этого восстановление реальных аккаунтов не включать.
9. Backup staging DB + files, восстановление в дополнительную изолированную БД,
   сравнение строк/хешей и ключа документов. Затем owner Resend/DNS и отдельное
   разрешение на контрольное письмо.
10. Зафиксировать SHA, метрики и результаты; до конца согласованного окна
    остановить staging compute. Не удалять данные без отдельного разрешения.

## Казахстан и production

По [официальному списку регионов](https://docs.railway.com/deployments/regions)
us-west2 — California, USA. Приложение, БД и оба тома находятся в этом регионе.
Размещение backup, логов, email и будущей Ollama отдельно не подтверждено.
Казахстана в опубликованном стандартном списке регионов Railway нет.

Текст [закона РК](https://adilet.zan.kz/rus/docs/Z1300000094) в текущей
машиночитаемой выдаче потребовал JavaScript; актуальная редакция и применимость
не удостоверены. Перед реальными клиентскими данными нужны правовая проверка
локализации/трансграничной передачи, подтверждение площадок/backup и договоров
обработчиков, включая Resend. **Коммерческий запуск заблокирован** до этого.
Локальная Ollama на зарубежном хосте сама по себе локализацию не обеспечивает.

Перед любым production обновлением: отдельное разрешение владельца, production
backup БД и файлов без раскрытия секретов, проверенное изолированное восстановление,
инвентаризация документов/ключей и безопасный план перехода старых файлов на
шифрование. Существующий DOCUMENT_ENCRYPTION_KEY не менять. Проверить совместимость
миграций с production schema и counts пользователей/компаний. Не запускать reset,
drop или разрушающие изменения. При rollback откатывать код, сохранять совместимые
добавленные колонки/таблицы; не восстанавливать устаревший dump поверх новых данных.
Старая production-ветка читает только bcrypt и plaintext-файлы: после записи
Argon2id/зашифрованных документов откат на неё несовместим. Нужен заранее
проверенный rollback-образ, поддерживающий новые форматы и RLS/MFA/authVersion.
Подробный порядок и ограничения: docs/production-update-plan.md.
