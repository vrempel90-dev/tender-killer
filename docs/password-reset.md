# Восстановление пароля и Resend

Реализованы /forgot-password, /reset-password?token=..., два POST API,
HTML/текст письма и настоящий серверный вызов Resend API. Реальные письма
в этой работе **не отправляются по указанию владельца**. До подключения
подтверждённого домена API возвращает одинаковый 503 для всех адресов.

## Механизм

- 32 случайных байта; PostgreSQL хранит SHA-256, срок 30 минут, sentAt/usedAt.
- Mail отправляется через Next after() после одинакового ответа, включая
  неизвестные адреса: задержка провайдера не выдаёт наличие пользователя.
  Ответ подтверждает только приём запроса и не обещает успешную отправку.
  При отсутствующей конфигурации страница объясняет недоступность, API
  отвечает одинаковым 503 без создания токена. Квоты возвращают Retry-After.
- Приём Resend подтверждает отправку провайдеру, не доставку в ящик.
  Токен активируется после ответа с acceptance ID. При ошибке удаляется
  неактивированный токен; прежняя доставленная ссылка остаётся действительной.
- Успешная повторная отправка отменяет старую ссылку. В транзакции сброса
  блокируется строка пользователя, атомарно расходуется токен, меняется пароль,
  отзываются все сессии и остальные токены. Текущий Argon2id сохранён.
- authVersion защищает даже от сессии со старым паролем, созданной во время
  сброса. Миграция bcrypt использует условную запись и не затирает новый пароль.
- MFA, коды восстановления, роль и компания сохраняются. Автовхода нет.
- PostgreSQL-квоты общие для реплик: отправка 3/аккаунт/30 минут,
  10/IP/30 минут, 200/платформу/час; сброс 30/IP/30 минут и 300/час.
  Railway использует X-Real-IP своего edge, конфликтующий X-Forwarded-For
  игнорируется. Для иного проверенного ingress оператор явно задаёт
  AUTH_TRUSTED_IP_HEADER=x-real-ip; вне этого контракта общая unknown-IP квота.
  Подставлять XFF разрешено исключительно loopback-тестам с APP_ENV=test.
  Поведение edge с поддельными заголовками дополнительно подтвердить на staging.
- APP_URL задаёт ссылку, Host не используется. Пароль 10–256 символов, буквы
  и цифра, обязательное совпадение подтверждения. Origin/content-type и лимит
  тела используют существующий middleware.

after() не является долговечной очередью: авария процесса до отправки может
потребовать повторного запроса пользователем. Автоповторов и записи
сырого токена в outbox нет. События password_reset_delivery_failed /
password_reset_job_failed должны попадать в мониторинг; payload/email не пишутся.
Плановое обслуживание удаляет истёкшие password_reset_tokens после согласованного
срока хранения, отдельно от существующих компаний и пользователей.

## Секреты и переменные Railway

На **отдельном** staging web service, затем после отдельного разрешения на production:

| Переменная | Значение |
|---|---|
| APP_URL | точный HTTPS origin приложения без пути/query/credentials |
| EMAIL_PROVIDER | resend |
| EMAIL_FROM | TENDER KILLER <security@auth.ВАШ-ДОМЕН> |
| EMAIL_DOMAIN_VERIFIED | false до подтверждения, затем true |
| RESEND_API_KEY | отдельный send-only ключ подтверждённого домена |
| APP_ENV | staging или production |

Ключ вводится только в защищённые Railway Variables; не в GitHub, PR или чат.
Существующие секреты не заменяются. Шаблон: deploy/railway/web.env.example.

## Подключение домена владельцем

1. Добавить в Resend принадлежащий владельцу домен/поддомен, например
   auth.ВАШ-ДОМЕН. Выбрать регион отправки с учётом правового основания
   трансграничной обработки email и содержания письма.
2. Скопировать из Domains точные DNS-записи:

| Назначение | Тип | Имя и значение |
|---|---|---|
| DKIM | TXT | selector._domainkey: точный публичный ключ из Resend |
| SPF | TXT | Return-Path поддомен: точное значение из Resend |
| Return-Path | MX | точный MX и priority из Resend |
| DMARC | TXT | _dmarc.auth.ВАШ-ДОМЕН; начать с v=DMARC1; p=none; rua=mailto:РЕАЛЬНЫЙ-ЯЩИК-ОТЧЁТОВ |

Не придумывать selector, DKIM-ключ или MX: они выдаются Resend после выбора
домена/региона. Не создавать вторую SPF-запись на том же имени; действующую
политику согласовать с остальными отправителями. Не менять MX основного
почтового домена ради transactional sending. После проверки DMARC
перевести на quarantine/reject, сохранив легитимных отправителей.

3. Дождаться Verified, отключить **open tracking и click tracking** на отдельном
   transactional поддомене: сброс не должен уходить через трекер.
4. Создать ограниченный API key; задать EMAIL_FROM и ключ в staging; после
   проверки DNS поставить EMAIL_DOMAIN_VERIFIED=true.
5. Отдельно получить от владельца email и разрешение на одно контрольное письмо.
   До этого реальные отправки запрещены. Подтвердить входящее письмо,
   SPF/DKIM/DMARC, HTTPS-ссылку, expiry/replay, новый пароль, отзыв сессий и MFA.

Официальные инструкции: [верификация домена](https://resend.com/docs/dashboard/domains/introduction),
[DMARC](https://resend.com/docs/dashboard/domains/dmarc),
[API](https://resend.com/docs/api-reference/emails/send-email).

## Токены, логи и браузер

Reset-страница не читает searchParams на сервере; клиент переносит токен
в память и сразу удаляет query через replaceState. Нет localStorage,
аналитики, сторонних шрифтов/картинок. no-referrer, no-store и noindex задаются
HTTP-заголовками, Next development logging исключает reset URL.

Первый запрос с query проходит CDN/ingress до выполнения приложения.
До публичного приёма необходимо подтвердить маскирование token/query
в Railway HTTP/access logs, traces, APM и настройках retention. Приложение
не может гарантировать это за внешний proxy. Неподтверждённая конфигурация —
блокер запуска восстановления для реальных пользователей. Провайдер email и
получатель по определению видят одноразовую ссылку.

## Автотесты без реальных писем

EMAIL_PROVIDER=test принимается только с APP_ENV=test и loopback APP_URL.
Endpoint строго http://127.0.0.1:PORT/email, без credentials/query/redirect.
scripts/test-email-sink.mjs хранит письма только в памяти и принимает только
адреса @example.test. Тестовый sink никогда не разворачивается в Railway.
На публичном staging email отключён до Resend.

Тесты: tests/password-reset.spec.ts, отдельный tests/unconfigured-email.spec.ts
и policy/transport Vitest. Второй сценарий запускает production-сборку с
EMAIL_PROVIDER=resend, EMAIL_DOMAIN_VERIFIED=false и пустыми ключом/отправителем:
503 одинаков для существующего и неизвестного адреса, токены не создаются,
форма показывает недоступность и не заявляет об отправке или доставке.
Покрыты одноразовость, expiry, replay/race, отказ отправки, MFA, старые сессии,
конкурентная сессия, новый/старый пароль, квоты, CSRF, мобильный интерфейс,
удаление query и no-referrer. Для запуска нужны отдельный local PostgreSQL,
ограниченная APP_DATABASE_URL, APP_URL/E2E_BASE_URL и email sink.
