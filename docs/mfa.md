# Второй фактор (MFA)

Документ описывает, что реализовано, какие решения приняты и что ещё не
сделано. Текущая политика на 17.10.2026: MFA добровольна для всех ролей.
Регистрация и обычный вход по e-mail/паролю сразу открывают приложение.
Старый флаг компании `requireMfaForAdmins` больше не заставляет подключать TOTP.
Добровольно включённый TOTP сохраняет защиту последующих входов.
Выход на всех устройствах и удаление своего аккаунта с повторным вводом пароля:
`/settings/account`. Старые staging-секреты аннулируются однократным строго
привязанным к validation скриптом `scripts/revoke-staging-totp.mjs`.

---

## 1. Что реализовано

| Возможность | Состояние |
| --- | --- |
| TOTP (приложение-аутентификатор) | готово |
| Коды восстановления | готово, 10 кодов, одноразовые |
| Требование MFA для OWNER и ADMIN | отключено по указанию владельца; legacy-флаг игнорируется, новые компании получают false |
| Признак пройденного фактора в сессии | готово, `sessions.mfaVerifiedAt` |
| Повторное подтверждение перед операцией (step-up) | механизм готов (`requireStepUp`), к операциям пока не подключён |
| Passkeys (WebAuthn) | **не реализовано**, см. раздел 6 |

## 2. Почему TOTP реализован без библиотеки

Код второго фактора — критический путь аутентификации. Внешняя библиотека
в этом месте расширяет поверхность цепочки поставок: обновление пакета
попадает прямо в проверку входа.

Реализация в `src/lib/auth/mfa/totp.ts` — это RFC 4226 (HOTP) и RFC 6238
(TOTP) поверх `node:crypto`, около 200 строк без зависимостей. Корректность
подтверждена контрольными векторами из самих стандартов:

- Base32 — RFC 4648, раздел 10;
- HOTP — RFC 4226, приложение D (`755224`, `287082`, `359152`, …);
- TOTP — RFC 6238, приложение B (`59 → 94287082`, `1111111109 → 07081804`, …).

Тесты: `src/lib/auth/mfa/__tests__/totp.test.ts`.

Единственная добавленная зависимость — `qrcode-generator@1.5.0` (MIT, без
собственных зависимостей) для QR-кода. Она не участвует в проверке кода:
только рисует картинку. QR собирается на сервере в SVG-путь
(`src/lib/auth/mfa/qr.ts`), в браузер уходит строка координат, разметку
строит React — готовый HTML в документ не вставляется.

## 3. Правило доступа

Политика — чистая функция `evaluateMfaGate` в `src/lib/auth/mfa/policy.ts`,
одна и та же для API, серверных страниц и UI:

| Фактор подключён | Обязателен для роли | Подтверждён в сессии | Результат |
| --- | --- | --- | --- |
| да | — | да | `OK` |
| да | — | нет | `VERIFY_REQUIRED` |
| нет | любой legacy-флаг | — | `OK` |
| нет | нет | — | `OK` |

Важное следствие второй строки: если пользователь подключил фактор
добровольно, его сессия всё равно обязана его пройти. Иначе включение
фактора не давало бы защиты.

Применение:

- `requireSession()` (`src/lib/auth/guard.ts`) — для API. Непройденный
  фактор даёт `403` и `details.mfaGate`, по которому клиент уводит
  пользователя на `/mfa`.
- `requirePageSession()` (`src/lib/auth/page-guard.ts`) — для серверных
  страниц. Здесь `redirect`, а не исключение: иначе вместо формы второго
  фактора пользователь видел бы экран ошибки.
- `requirePartialSession()` — только там, где фактор ещё не может быть
  пройден: подключение, подтверждение, статус, выход.

Пароль проверен ≠ доступ открыт: `/api/auth/login` создаёт сессию, но без
`mfaVerifiedAt`. Такая сессия не проходит через `requireSession`.

## 4. Защита от повтора и перебора

| Угроза | Мера |
| --- | --- |
| Повторное предъявление перехваченного кода TOTP | `users.totpLastCounter`: шаг времени, на котором код сработал, фиксируется; код того же или более раннего шага отклоняется |
| Повторное использование кода восстановления | `recovery_codes.usedAt`; сравнение идёт по всем кодам без досрочного выхода, чтобы не утекало время |
| Перебор кода | `consumeQuota('mfa-verify', userId, 10, 900)` — 10 попыток за 15 минут; лимиты атомарны между репликами |
| Снятие защиты из перехваченной сессии | отключение требует действующего кода; при обязательном по политике факторе отключение запрещено совсем |
| Утечка хеша кода восстановления | Argon2id, параметры как у пароля (`memoryCost: 19456`) |
| Блокировка себе доступа при неверном сканировании QR | фактор включается только после подтверждения кодом; до подтверждения секрет записан, но фактор выключен |

Все события пишутся в журнал операций: `MFA_ENROLL_START`, `MFA_ENABLED`,
`MFA_VERIFIED`, `MFA_VERIFY_FAILED`, `MFA_RECOVERY_CODE_USED`,
`MFA_RECOVERY_CODES_REISSUED`, `MFA_DISABLED`.

## 5. Проверки

Модульные (`npm test`): 70 тестов в `src/lib/auth/mfa/__tests__` —
контрольные векторы RFC, политика доступа, одноразовость кодов, QR.

Сквозные (`tests/mfa.spec.ts`, запускаются в CI вместе с `security.spec.ts`):

1. владелец без фактора не читает и не создаёт данные (403 + `mfaGate`),
   и запись действительно не появляется в БД;
2. после подключения доступ открывается в той же сессии;
3. новая сессия обязана подтвердить фактор; код, которым подключали
   фактор, повторно не принимается;
4. код восстановления срабатывает один раз, остаток уменьшается, во второй
   сессии тот же код отклоняется;
5. обязательный по политике фактор нельзя отключить; неверный код не
   отключает фактор;
6. все операции с фактором недоступны без авторизации.

## 6. Чего нет: passkeys

Passkeys (WebAuthn) не реализованы. Это осознанно отложено, а не забыто:

- для них нужен серверный компонент проверки attestation и подписи
  (`@simplewebauthn/server` либо собственная реализация на COSE/CBOR),
  отдельная таблица зарегистрированных ключей, привязка к Relying Party ID
  (домену) и сценарий восстановления при потере всех устройств;
- Relying Party ID жёстко привязан к домену, а решение о размещении
  (раздел «Казахстанский хостинг» в `docs/release-gates.md`) ещё не
  принято: ключи, зарегистрированные на временном домене, после переезда
  перестанут работать.

Поэтому порядок такой: TOTP закрывает требование второго фактора сейчас,
passkeys добавляются после фиксации домена. В схеме БД для них уже есть
место: модель `RecoveryCode` и поля сессии не зависят от типа фактора.

## 7. Что это меняет для существующих сценариев

Регистрация создаёт владельца компании, для которого фактор обязателен.
Поэтому после `/api/auth/register` и `/api/auth/login` сервер возвращает
`next` — `/mfa` или `/dashboard`; формы входа и регистрации идут туда, куда
указал сервер, а не на фиксированный адрес.

Сквозные тесты, которые работают от имени владельца, подключают фактор
настоящим кодом (`tests/security.spec.ts`, `tests/workflow.spec.ts`).
Проверка не обходится и не отключается.
