# Вход владельца в тестовую версию

Адрес: https://tk-validation-web-staging.up.railway.app/login.

Это отдельный проект Railway `tender-killer-validation`, environment `staging`.
Production — проект `tender-killer`, environment `production`, другой web,
Postgres и том документов. Существующий production-аккаунт автоматически
не появляется в staging. Ошибка 401 означает неверные для этой базы данные;
после десяти попыток за фиксированное окно 900 секунд API отвечает 429.
`Retry-After` содержит оставшиеся секунды, форма округляет их вверх до минут.
Повторная заблокированная попытка не продлевает окно. Лимиты не увеличены.

## Получить тестовый доступ

1. Открыть указанный адрес и проверить отметку **TENDER KILLER — TEST / STAGING**.
2. Нажать «Зарегистрировать компанию» (или открыть `/register`). Создать свою
   тестовую компанию; БИН/ИИН можно оставить пустым. Указать свою почту и
   **новый отдельный тестовый пароль**: 10–256 символов, буквы и цифры.
   Можно использовать тот же email, что в production: базы раздельные.
3. После регистрации откроется `/mfa`. Добавить QR-код в приложение
   аутентификации, подтвердить текущий шестизначный код. Сохранить показанные
   одноразовые коды восстановления в менеджере паролей.
4. После подтверждения доступны функции своей компании. При следующем входе
   использовать тестовый пароль и новый код MFA. Если сработал лимит — дождаться
   времени, указанного формой. Поддерживаются и одноразовые recovery-коды MFA.
5. Загружать только синтетические или разрешённые тестовые материалы.

Используется существующая штатная регистрация: она атомарно создаёт новую
компанию и OWNER с обязательной MFA. Административный bootstrap не нужен,
скрытые аккаунты и пароли отсутствуют. Ничего не копируется из production:
ни документы/тендеры, ни пароли/хеши, ни сессии или MFA-секреты. Существующая
регистрация production не меняет свою политику; email дополнительно нормализуется
до проверки. На основном сайте продолжают использоваться прежние реквизиты.
Уже занятый **тестовый** email нельзя перезаписать регистрацией.

## Восстановление пароля

`/forgot-password` использует отдельную конфигурацию почты этой среды.
Нужны `EMAIL_PROVIDER=resend`, подтверждённый отправитель `EMAIL_FROM`,
`EMAIL_DOMAIN_VERIFIED=true` и защищённый `RESEND_API_KEY`. Настройка в
`docs/password-reset.md`. Подключение реальной почты этой задачей не выполняется.

Без этих условий сервер возвращает одинаковый 503 для известного и неизвестного
адреса; токен не создаётся. При превышении общей квоты возможен 429 с
`Retry-After`. UI не утверждает, что письмо отправлено. С настроенным sender
возвращается нейтральное «запрос принят»: отправка идёт после ответа, поэтому
по статусу и задержке нельзя определить наличие аккаунта. Сбой доставки
фиксируется без адреса, ссылки, пароля или токена. MFA сбросом не снимается.

## Настройка и проверка оператором

- Баннер определяется **при запросе**, а не при сборке: `APP_ENV=staging` или
  Railway environment `staging`. Railway environment `production` всегда
  скрывает баннер. В остальных средах баннер выключен по умолчанию.
- Runtime web должен использовать отдельную staging-БД и ограниченную роль
  NOBYPASSRLS; строку подключения нельзя переносить из production.
- Изменений схемы Prisma и миграций нет. Обновлять/сбрасывать существующие
  записи, пользователей, пароли или глобальные квоты для этой задачи не нужно.
- `npm run verify`: типы, lint, unit. `tests/auth.spec.ts` проверяет HTTP и UI;
  существующие MFA/RLS/password-reset тесты дополняют его. Quality и Security
  запускаются на PR. Тесты отправки используют только локальный test sink,
  синтетические пароли, адреса и токены.
- `STAGING_BASE_URL=https://tk-validation-web-staging.up.railway.app node scripts/staging-auth-acceptance.mjs`
  проверяет настоящий staging: регистрацию двух изолированных компаний,
  первый/повторный вход, выход, MFA, одинаковые 401, rate limit и реальное
  истечение блокировки (до 15 минут). Никаких тестовых обходов времени или
  сброса квот на сервере. Скрипт ограничен точным staging-origin, требует
  баннер до создания аккаунтов и не обращается к production. Учётные записи
  остаются только синтетическими; их случайные пароли/секреты не печатаются.

В конфигурации Railway значения секретов недоступны OAuth-коннектору:
он позволяет подтвердить отдельные ресурсы и имена переменных, но не сравнить
байт-в-байт DATABASE_URL. Рабочая изоляция дополнительно проверяется HTTP
с двумя компаниями; production deployment/config сверяются до и после работы.
