# Изоляция данных компаний в БД

Документ описывает второй рубеж изоляции — на уровне PostgreSQL.
Состояние на 15.10.2026.

Первый рубеж (фильтр по `companyId` в каждом запросе и проверка сессии на
сервере) остаётся. Он защищает от обращения к чужим данным по прямой
ссылке. Но он держится на дисциплине: достаточно одного запроса без
фильтра, чтобы утекли данные другой компании. Второй рубеж убирает эту
зависимость от аккуратности.

---

## 1. Что сделано

| Мера | Состояние |
| --- | --- |
| Row Level Security на таблицах данных компаний | включён, 15 таблиц |
| Политика «нет переменной — нет строк» (отказ закрытый) | да |
| Роль приложения без права менять структуру БД | `scripts/db-roles.sql` |
| Роль приложения с `NOBYPASSRLS` | да, проверяется скриптом и тестом |
| Разделение роли миграций и роли приложения | да, в `docker-compose.yml` |
| Проверка изоляции в обход приложения | `tests/rls.spec.ts`, 8 тестов |

## 2. Как работает

Политика каждой таблицы сравнивает компанию строки с переменной сессии
`app.company_id`:

```sql
CREATE POLICY tenant_isolation ON "tenders" FOR ALL
  USING ("companyId" = current_setting('app.company_id', true))
  WITH CHECK ("companyId" = current_setting('app.company_id', true));
```

`current_setting(..., true)` при неустановленной переменной возвращает
NULL, сравнение даёт false — не видно ни одной строки. Это важно: ошибка
конфигурации приводит к отказу в доступе, а не к доступу ко всему.

`WITH CHECK` закрывает запись: создать или перенести строку в другую
компанию нельзя даже прямым SQL.

Дочерние таблицы (`document_extractions`, `requirements`, `line_items`,
`compliance_findings`, `supplier_quote_items`, `financial_models`,
`contract_analyses`, `contract_risks`, `compliance_runs`) своего
`companyId` не имеют. Их политика ссылается на родителя:

```sql
USING (EXISTS (SELECT 1 FROM "tenders" t WHERE t."id" = "tenderId"))
```

Подзапрос выполняется той же ролью, поэтому к нему применяется политика
родителя. Строка видна тогда и только тогда, когда виден её родитель —
правило не нужно дублировать.

Полный список таблиц и политик — миграция
`prisma/migrations/20261015190000_rls_tenant_isolation`. Тест
«все таблицы с данными компаний защищены политикой» перечисляет их
повторно и падает, если новая миграция добавит таблицу без политики.

## 3. Откуда берётся `app.company_id`

Переменная устанавливается в `src/lib/db.ts` расширением Prisma Client:
перед каждой операцией над таблицей компании в той же транзакции
выполняется `set_config('app.company_id', …, true)`. Одна транзакция
нужна потому, что иначе `set_config` и запрос могут уйти по разным
соединениям пула.

Идентификатор берётся из **подписанного cookie сессии** (HS256,
`SESSION_SECRET`). Подделать его без секрета нельзя, а от клиента в явном
виде он не приходит никогда. Отзыв сессии и активность пользователя
проверяются отдельно, в `getCurrentSession`.

Почему не контекст выполнения (`AsyncLocalStorage`): `enterWith` действует
только в текущем асинхронном контексте. Установка внутри awaited-функции
(проверки доступа) не доживает до кода вызывающего, и запрос уходил бы без
переменной — то есть под ролью приложения возвращал бы пустой результат.
Это проверено на практике: сквозные тесты падали с ошибкой «запрос вне
контекста компании». Cookie же доступно в любой точке обработки запроса.

Проверка подписи кэшируется на минуту по значению токена: в одном
HTTP-запросе к БД обращаются несколько раз, и проверять одну и ту же
подпись заново не нужно. Размер кэша ограничен 500 записями.

Если компания не определена и контекст не объявлен явно, операция
**падает с понятной ошибкой**, а не возвращает пустой результат: иначе
забытая привязка выглядела бы как «данных нет».

Для работы вне HTTP-запроса есть два явных выхода:

- `runWithTenant(companyId, fn)` — фоновая работа для конкретной компании;
- `runUnscoped(fn)` — обслуживание и импорт справочников.

Транзакции из нескольких операций пишутся через `dbTransaction(fn)`:
переменная устанавливается один раз на транзакцию, а операции идут на
транзакционном клиенте без расширения — иначе получилась бы вложенная
транзакция.

## 4. Роль приложения

`scripts/db-roles.sql` создаёт группу прав `tk_app` и учётную запись
приложения:

- `NOBYPASSRLS` — иначе политики к роли не применяются (скрипт проверяет
  это и падает, если флаг выставлен);
- `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`;
- `SELECT/INSERT/UPDATE/DELETE` на таблицы, но **нет** `CREATE` в схеме:
  DDL выполняют только миграции;
- нет доступа к `_prisma_migrations`;
- `ALTER DEFAULT PRIVILEGES` — таблицы будущих миграций получают те же
  права автоматически.

Запуск (однократно, под ролью с правом CREATEROLE):

```sh
psql "$ADMIN_DATABASE_URL" \
  -v app_user="$APP_DB_USER" -v app_password="$APP_DB_PASSWORD" \
  -f scripts/db-roles.sql
```

Скрипт идемпотентен. Порядок развёртывания: миграции и сиды под владельцем
схемы → `db-roles.sql` → запуск приложения под ограниченной ролью.
В `docker-compose.yml` этот порядок задан зависимостями сервисов.

Владелец схемы RLS обходит (это штатное поведение PostgreSQL для
владельца таблицы), поэтому `db:deploy` и `db:seed` работают как раньше.

## 5. Что намеренно не покрыто

Таблицы аутентификации — `companies`, `users`, `sessions`,
`recovery_codes`, `password_reset_tokens`, `audit_logs` — политиками не покрыты.

Причина: к ним обращаются **до** того, как компания известна. Вход по
e-mail и паролю ищет пользователя по e-mail; неудачная попытка входа
пишется в журнал; регистрация создаёт компанию. Политика, требующая
`app.company_id`, сделала бы вход невозможным, а политика вида «если
переменной нет — разрешить» не давала бы никакой защиты и при этом
создавала бы ложное ощущение, что таблица защищена.

Эти таблицы защищены первым рубежом: все выборки пользователей и журнала
фильтруются по `companyId` из сессии, что подтверждено сквозными тестами
изоляции (`tests/security.spec.ts`).

Что ещё остаётся сделать:

- для `users` и `audit_logs` возможна отдельная политика с исключением
  только для операций аутентификации (например, через отдельную роль с
  доступом к функции поиска пользователя по e-mail). Решение требует
  изменения схемы доступа и отдельной проверки;
- шифрование данных на уровне столбцов и управление ключами не сделаны и
  зависят от выбора хостинга (см. `docs/release-gates.md`).

## 6. Проверки

`tests/rls.spec.ts` подключается к БД **напрямую ролью приложения**, в
обход кода приложения:

1. без `app.company_id` не видно ни одной строки;
2. с установленной компанией видны только её строки;
3. `INSERT` для другой компании отклоняется (`WITH CHECK`);
4. `UPDATE`, переносящий строку в другую компанию, отклоняется;
5. `DELETE` чужой строки не затрагивает ничего;
6. дочерние записи наследуют видимость родителя;
7. роль не обходит RLS, не создаёт таблиц, не отключает RLS и не читает
   журнал миграций;
8. все 15 таблиц данных компаний имеют включённый RLS и политику.

Тест требует `APP_DATABASE_URL`. В CI его отсутствие — ошибка, а не
причина пропустить проверку: иначе изоляция осталась бы непроверенной.

В CI сервер приложения для сквозных тестов запускается **под ограниченной
ролью**, поэтому `tests/security.spec.ts` и `tests/mfa.spec.ts` проходят
уже с действующим RLS.
