# Резервное копирование и восстановление

Состояние на 15.10.2026: процедура реализована и **проверена учебным
восстановлением** на локальной установке. На целевой инфраструктуре
проверку нужно повторить — хостинг ещё не выбран
(см. `docs/release-gates.md`).

Непроверенная резервная копия — это не резервная копия. Поэтому здесь не
только скрипты, но и сценарий учебного восстановления, который сверяет
результат построчно и отдельно убеждается, что испорченная копия
отвергается.

---

## 1. Что входит в копию

Обновление 17.10.2026: HMAC создаёт `scripts/backup-auth.mjs`, ключ выведен
независимым PBKDF2-SHA512 (600000 итераций, случайная соль). Пароль не передаётся
в argv. Sidecar имеет версию `tk-backup-mac-v2`, не зависит от имени/пути файла.
Старые raw-HMAC копии сохраняются, но новый restore отклоняет их: для переноса
нужен контролируемый изолированный restore прежней версией и новая шифрованная
копия. Не заменяйте sidecar без проверки исходной копии. Документный ключ всегда
хранится отдельно. CI проверяет полный PostgreSQL backup/restore и подмену.

| Объект | Входит | Примечание |
| --- | --- | --- |
| Схема и данные БД | да | `pg_dump --format=custom`, включая политики RLS |
| Документы пользователей | да | архив `STORAGE_DIR` |
| Опись копии | да | версия `pg_dump`, последняя миграция, число применённых миграций |
| Роли БД и пароли | **нет** | роли живут на уровне кластера; создаются `scripts/db-roles.sql` |
| `DOCUMENT_ENCRYPTION_KEY` | **нет** | см. раздел 3 |
| `SESSION_SECRET`, ключи API | **нет** | секреты хранятся вне копии |

Роли намеренно не входят: копия, из которой можно восстановить и данные, и
учётные записи доступа к ним, — это один объект, утечка которого отдаёт
всё сразу.

## 2. Шифрование копии

Схема — **encrypt-then-MAC**:

1. `openssl enc -aes-256-cbc -pbkdf2 -iter 600000 -md sha512 -salt`;
2. `openssl dgst -sha256 -hmac` по шифротексту в отдельный файл `.hmac`.

Восстановление сначала проверяет HMAC и только потом расшифровывает.
Порядок важен: иначе повреждённые или подменённые байты попали бы в
расшифровщик, а оттуда — в базу.

Парольная фраза — `BACKUP_ENCRYPTION_PASSPHRASE`, минимум 20 символов.
Без неё копирование **отказывается работать**: незашифрованная копия на
стороннем хранилище обесценивает остальную защиту.

Файлы документов попадают в архив уже зашифрованными ключом документов.
Копия шифруется повторно, потому что в путях файлов есть идентификаторы
компаний — то есть сама структура архива раскрывает состав клиентов.

## 3. Ключ документов: главное предупреждение

`DOCUMENT_ENCRYPTION_KEY` в копию не входит. Последствия:

- **без этого ключа восстановленные документы не прочитать**, даже если
  база и файлы восстановлены полностью;
- ключ нужно хранить отдельно от копий. Если ключ лежит рядом с копией,
  одна утечка хранилища отдаёт и файлы, и способ их прочитать.

Перед тем как считать восстановление успешным, проверьте, что доступен
тот же ключ, что был при загрузке документов.

## 4. Команды

```sh
# Копия (БД + документы), с удалением устаревших
npm run backup

# Восстановление в базу из RESTORE_DATABASE_URL
RESTORE_DATABASE_URL=... RESTORE_STORAGE_DIR=... \
  npm run restore -- ./backups/20261015T183538Z

# Учебное восстановление: копия → отдельная база → сверка
VERIFY_DATABASE_URL=... npm run backup:verify
```

`RESTORE_DATABASE_URL` — отдельная переменная, а не `DATABASE_URL`,
намеренно: восстановление перезаписывает объекты, и случайный запуск не
должен затереть рабочую базу. `backup:verify` дополнительно отказывается
работать, если `VERIFY_DATABASE_URL` совпадает с рабочей базой.

## 5. Что проверяет учебное восстановление

`scripts/backup-verify.sh`, 8 шагов:

1. копия создаётся без ошибок;
2. в зашифрованном дампе не видно сигнатуры `PGDMP` — содержимое
   действительно закрыто;
3. восстановление в отдельную базу проходит;
4. **количество строк совпадает по всем таблицам** (считается запросом по
   каждой таблице, а не по приблизительной статистике планировщика);
5. политики RLS восстановлены вместе со схемой, и у всех таблиц с
   политиками включён RLS;
6. файлы документов совпадают **побайтово** (sha256 по каждому файлу);
7. копия с одним изменённым байтом **отвергается проверкой HMAC**, причём
   до расшифровки;
8. копия с неверным паролем не восстанавливается.

Результат прогона на локальной установке (15.10.2026): пройдено
полностью — 23 таблицы совпали по числу строк, 15 политик RLS на месте,
4 файла документов идентичны, повреждение и неверный пароль отклонены.

## 6. После восстановления

1. создать роль приложения: `scripts/db-roles.sql` (роли не в копии);
2. убедиться, что `DOCUMENT_ENCRYPTION_KEY` — тот же;
3. подтвердить изоляцию: `npm run test:e2e -- tests/rls.spec.ts`;
4. сессии пользователей остаются в БД. Если копия старше инцидента,
   разумно отозвать все сессии: `UPDATE sessions SET "revokedAt" = now()
   WHERE "revokedAt" IS NULL`.

## 7. Расписание и хранение

Скрипты не содержат расписания: оно зависит от инфраструктуры. Пример
для cron (ежедневно в 03:17, со смещением от круглого часа, чтобы не
совпадать с общей нагрузкой):

```cron
17 3 * * * cd /opt/tender-killer && \
  BACKUP_DIR=/var/backups/tender-killer npm run backup >> /var/log/tk-backup.log 2>&1
```

По умолчанию хранится 14 последних копий (`BACKUP_KEEP`). Копии
складываются в каталог с правами `0700`, файлы — `0600`; каталог
`/backups` исключён из Git.

## 8. Что остаётся решить

| Работа | Почему не сделано |
| --- | --- |
| Хранение копий вне машины приложения | зависит от выбора хостинга и требований к региону хранения данных |
| Непрерывное архивирование WAL (point-in-time recovery) | сейчас RPO равен интервалу между копиями; PITR требует постоянного хранилища WAL на выбранной платформе |
| Регулярное автоматическое учебное восстановление | скрипт есть, расписание зависит от инфраструктуры |
| Целевые RPO/RTO как обязательство | нельзя зафиксировать до выбора платформы; сейчас измерено только на локальной установке |
| Регламент реагирования на инцидент | отдельная работа, в `docs/release-gates.md` как P0 |
