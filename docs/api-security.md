# Безопасность API

Обзор того, что защищает интерфейс приложения, и что остаётся. Состояние
на 15.10.2026.

---

## 1. На входе: proxy.ts

| Проверка | Для чего |
| --- | --- |
| Origin запроса совпадает с `APP_URL`; `Sec-Fetch-Site: cross-site` отклоняется | CSRF для изменяющих запросов |
| `APP_URL` обязателен в production и обязан быть HTTPS | иначе проверка Origin ничего не значит |
| Content-Type только `application/json` или `multipart/form-data` | простые формы со сторонних сайтов не доходят до обработчика |
| Content-Security-Policy с одноразовым nonce | XSS |

CSP строится в `proxy.ts`, а не в `next.config.ts`, потому что строгая
политика требует nonce на каждый ответ. Без nonce пришлось бы разрешить
`script-src 'unsafe-inline'`, что обесценивает защиту: внедрённый в
страницу скрипт исполнился бы наравне со своими. Next подставляет nonce в
свои теги `script`, читая заголовок запроса.

Политика для страниц: `default-src 'self'`, `script-src 'self'
'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'self'`,
`form-action 'self'`, `frame-ancestors 'none'`, `connect-src 'self'`.
В разработке добавляются `'unsafe-eval'` и `ws:` — без них не работает
горячая перезагрузка Turbopack; в production их нет.

Ответы API получают `default-src 'none'; sandbox`: это JSON, ему ничего не
нужно.

Известное ослабление: `style-src 'unsafe-inline'`. Next и Tailwind
вставляют стили инлайн, а nonce для стилей Next не ставит. Инъекция стиля
опаснее всего при наличии XSS, которую закрывает `script-src`.

## 2. Заголовки ответов

`next.config.ts` для всех ответов: `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY`, `Referrer-Policy: same-origin`,
`Permissions-Policy` (камера, микрофон, геолокация выключены),
`Cross-Origin-Opener-Policy: same-origin`,
`Cross-Origin-Resource-Policy: same-origin`. В production добавляется
`Strict-Transport-Security: max-age=63072000; includeSubDomains`.

Все ответы API — успешные и с ошибками — отдаются с
`Cache-Control: private, no-store`: они зависят от сессии.

## 3. Доступ

| Уровень | Механизм |
| --- | --- |
| Авторизация | подписанный JWT в httpOnly cookie + реестр сессий в БД с возможностью отзыва |
| Второй фактор | обязателен для OWNER/ADMIN; сессия без подтверждения не проходит guard (`docs/mfa.md`) |
| Роли | OWNER > ADMIN > ANALYST > VIEWER; запись — от ANALYST |
| Изоляция компаний | фильтр по `companyId` из сессии в каждом запросе + Row Level Security в БД (`docs/db-isolation.md`) |
| Ошибки доступа | 401 без сессии, 403 при нехватке прав, **404** при обращении к объекту другой компании — существование объекта не раскрывается |

`companyId` никогда не приходит от клиента: он берётся из проверенной
сессии, а для политик БД — из подписанного cookie.

## 4. Пределы запросов

Лимиты атомарны между репликами (`request_quotas`, `INSERT … ON CONFLICT`),
отказ закрытый: если лимит не настроен, запрос отклоняется (503), а не
пропускается.

| Операция | Предел |
| --- | --- |
| Вход, глобально | 500 за минуту |
| Вход, на учётную запись | 10 за 15 минут |
| Регистрация | 40 за час |
| Второй фактор: проверка кода | 10 за 15 минут на пользователя |
| Второй фактор: подключение и подтверждение | 10 за 15 минут |
| Перевыпуск кодов восстановления | 5 за час |
| Загрузка документа | 30 за час на компанию |
| Повторный разбор документа | 30 за час на компанию |
| Импорт истории закупок | 20 за час на компанию |
| Финансовый расчёт | 120 за минуту на компанию |
| **Любое изменение данных** | **300 за минуту на компанию** |

Последняя строка — страховка в `requireWriteAccess`: новый обработчик
записи получает предел автоматически, даже если про собственный лимит
забудут. Одновременный разбор документов дополнительно ограничен арендой
(одна на компанию, четыре на установку).

## 5. Тело запроса

Размер тела считается по фактически прочитанным байтам, а не по
`Content-Length` (его можно подделать): `readBoundedBody`, предел 1 МиБ
для JSON и `MAX_UPLOAD_BYTES` для файлов, с тайм-аутом чтения 30 секунд.
Все входные данные разбираются схемами Zod; при несоответствии — 422 с
перечнем полей.

## 6. Ответы об ошибках

Внутренние ошибки отдаются как «Внутренняя ошибка сервера» с
идентификатором; в журнал пишется только класс ошибки и этот
идентификатор — ни SQL, ни текст документа, ни учётные данные. Вне
production текст ошибки дополнительно печатается в консоль разработчика.

Ошибки целостности хранилища и отсутствия ключа шифрования имеют
отдельные понятные ответы (500 и 503): это состояние инфраструктуры, а не
ошибка запроса.

## 7. Проверено тестами

`tests/security.spec.ts`: чужой Origin и неверный Content-Type
отклоняются до изменения cookie; перебор пароля упирается в лимит;
некорректный JSON отклоняется; данные и файлы другой компании дают 404 на
чтение, скачивание, удаление и повторный разбор; VIEWER не пишет; выход
отзывает сессию на сервере; аренда парсера не протекает.

`tests/mfa.spec.ts`, `tests/rls.spec.ts` — см. `docs/mfa.md` и
`docs/db-isolation.md`.

## 8. Что остаётся

| Работа | Состояние |
| --- | --- |
| `style-src 'unsafe-inline'` | ослабление; убирается только переводом стилей Next на nonce |
| Независимый внешний аудит API | не проводился |
| Пределы на уровне пользователя (а не только компании) | не сделаны: сейчас лимит общий на компанию |
| Защита от автоматизированной регистрации (CAPTCHA или приглашения) | не сделана; есть только лимит 40 в час |
